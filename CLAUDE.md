## 1. О проекте

**There and Back** — мобильное приложение-«путешествие на шагах».

Пользователь выбирает маршрут (путь из точки **A** в точку **B**). Реальные шаги,
снятые с датчиков телефона, конвертируются в пройденное расстояние и **двигают
фигурку игрока по маршруту**. Цель — дойти до точки B.

Ключевая метафора: приложение не про фитнес-метрики, а про **прогресс в пути**.
Пользователю показывают не «8412 шагов», а «День 5, 5.23 километра, Halfling
Country, перешёл ручей по узкому мостику». Числа в UI всегда завёрнуты в язык
путешествия.

Социальная часть: пользователь добавляет друзей и видит, кто где идёт по тому же
маршруту — на карте пинами и в таблице.

### 1.1 Сеттинг

Каталог квестов может включать два типа сеттингов:

1. **Собственные вымышленные фэнтези-миры** — свои регионы, ориентиры, нарратив.
2. **Сюжеты произведений в общественном достоянии** (мифология, классическая
   литература — например, «Одиссея» Гомера, ~VIII век до н.э.). Такие
   произведения не защищены ни авторским правом, ни товарными знаками — их
   имена и география можно использовать свободно.

> **Важно.** Референсные скриншоты (см. §2.1) взяты из приложения с тонко
> замаскированным толкиновским сеттингом («Mount Fire», «Halfling Country»,
> «Mr Underhill»). Мы копируем **структуру и UX**, но не переиспользуем и не
> «маскируем» сеттинг **защищённых авторским правом вселенных** — Толкин,
> Роулинг и любые другие произведения, где жив автор или не истёк срок
> охраны. Никаких их имён, топонимов, рас, артефактов и формулировок — ни в
> контенте, ни в примерах, ни в тестовых данных. Перед тем как использовать
> любое стороннее произведение как сеттинг квеста — сначала проверить статус
> охраны (страна публикации, дата смерти автора, товарные знаки), а не
> полагаться на «это же старая книга» на глаз.
>
> Первый квест в каталоге — **«The Odyssey: Troy to Ithaca»**
> (`assets/journeys/odyssey-ithaca/`, черновик локаций и нарратива —
> `journeys/odyssey-ithaca/locations.json` в рабочих материалах). Остальные
> квесты каталога — собственный фэнтези-мир; название мира и регионов ещё не
> придумано (см. §14).

## 2. Референс и UX

### 2.1 Что взято из референса

Разработка ведётся с оглядкой на скриншоты-референс, которые задают направление:

- Тёмная тема, почти чёрный фон, **золотой акцент** и антиквенный serif-шрифт.
- Главный экран — **силуэтный пейзаж**: чёрный передний план, цветные слои
  холмов, градиентное небо, маленькая фигурка путника с посохом.
- Крупные цифры расстояния золотом, под ними — регион и одна строка нарратива
  курсивом.
- Счётчик «День N» от старта квеста.
- Экран статистики — **рисованная карта** в стиле чернильной иллюстрации:
  пунктирная тропа, нарисованные ориентиры, цветные пины друзей.
- Пять вкладок внизу.

### 2.2 Чего в референсе нет и что мы делаем иначе

- Свой сеттинг и свои названия (§1.1).
- Нормальная работа офлайн и внятная обработка отказа в разрешениях (§7).

## 3. Платформы и стек

| Слой | Выбор |
|---|---|
| Платформы | iOS и Android, одна кодовая база |
| Framework | **Flutter** (stable, ≥ 3.47 / Dart ≥ 3.13) |
| Язык | Dart |
| Сцена главного экрана | **Flame** (`flame` ^1.38) — `ParallaxComponent` |
| Состояние | **Riverpod** (`flutter_riverpod` + `riverpod_generator`) |
| Модели / DTO | `freezed` + `json_serializable` |
| Навигация | `go_router` |
| Локальное хранилище | `drift` (SQLite) — источник правды офлайн |
| Шаги | `health` (^13.x) — HealthKit на iOS, Health Connect на Android |
| Карта | **своя рисованная иллюстрация**, `InteractiveViewer` (см. §6.2) |
| Бэкенд | **Firebase**: Auth, Cloud Firestore, Cloud Functions, FCM |
| Аналитика/краши | Firebase Analytics + Crashlytics |
| Тесты | `flutter_test`, `mocktail`, `integration_test` |
| Лок-скрин уведомление (Android) | `flutter_local_notifications` (§7, `docs/screens/lock-screen.md`) |
| Фоновый синк (Android) | `workmanager` (§7, `docs/screens/lock-screen.md`) |

### Почему так

- **Flutter, а не React Native** — главный экран это анимированная сцена с
  постоянной перерисовкой. Flutter рисует всё сам через Impeller, кадры
  стабильнее. Плюс `health` даёт **единый API** поверх HealthKit и Health
  Connect; в RN пришлось бы держать две разные библиотеки и писать обёртку
  вручную.
- **Flame, а не самописный `CustomPainter`** — `ParallaxComponent` уже умеет
  многослойный фон с разными скоростями, бесшовное зацикливание и корректный
  game loop. Не изобретать заново.
- **Никакого `flutter_map` / OSM / Google Maps.** Карта — вымышленный мир,
  тайлы реальной планеты не нужны. Это минус тяжёлая зависимость, минус сетевые
  запросы, и офлайн-работа получается бесплатно.
- **Health Connect, не Google Fit** — Google Fit API устарел (регистрация новых
  приложений закрыта с 1 мая 2024), в `health` его поддержка удалена начиная с
  версии 11.0.0. **Никогда не предлагать Google Fit.**
- **Firebase** — Auth + Firestore + FCM закрывают друзей, синк и пуши в MVP без
  своего сервера.

## 4. Архитектура

**Feature-first**, три слоя внутри каждой фичи.

```
lib/
  main.dart
  app/                 # роутер, тема, DI-корень, bootstrap
  core/                # общее: ошибки, форматтеры, extensions, константы
  design/              # дизайн-система: цвета, типографика, компоненты
  data/                # drift-схема, Firestore-репозитории, health-адаптеры
  features/
    journey/           # маршрут, прогресс, главный экран
      domain/          # сущности + чистые функции, БЕЗ Flutter-импортов
      data/            # репозитории, мапперы
      presentation/    # виджеты, Flame-компоненты, Riverpod-провайдеры
    steps/             # чтение шагов, синхронизация, дельты
    quest_map/         # рисованная карта, статистика квеста, ETA
    achievements/      # трофеи
    friends/           # друзья, таблица прогресса
    profile/           # настройки
  l10n/                # локализация (ru, en)
assets/
  journeys/{journeyId}/
    map.webp           # рисованная карта маршрута
    map.json           # путь, ориентиры, привязка к прогрессу
    segments/          # слои пейзажа по сегментам
```

Правила слоёв:

- `domain/` не импортирует `package:flutter/*`, Firebase и `health`. Только
  чистый Dart. Вся математика прогресса живёт здесь и покрыта unit-тестами.
- UI никогда не ходит в репозиторий напрямую — только через Riverpod-провайдер.
- Firestore-модели и доменные сущности **разные типы**. Маппинг в `data/`.

## 5. Доменная модель

```dart
Journey       // квест: id, название, общая длина (метры), сегменты, ассеты карты
Segment       // участок маршрута: диапазон [fromMeters, toMeters], регион, биом, набор слоёв
NarrativeBeat // строка нарратива, привязанная к позиции в метрах
Landmark      // нарисованный ориентир на карте: позиция вдоль пути + координаты на картинке
Progress      // сколько метров пройдено по конкретному квесту, дата старта, дата завершения (если дошёл до B)
StepSample    // сырой отрезок шагов: from, to, steps, source
UserProfile   // id, ник, аватар, длина шага, приватность
Friendship    // связь двух пользователей, статус (pending/accepted/blocked)
Achievement   // трофей: условие, дата получения
```

### 5.1 Шаги → расстояние

Единственное место конвертации — `features/journey/domain/stride.dart`.

- **Онбординг ничего не спрашивает про длину шага.** Дефолт для всех —
  **0.75 м**, без вопросов про рост и пол. Точность калибруется позже.
- Пользователь может задать длину шага вручную в профиле (§6.5) — ручное
  значение всегда приоритетнее дефолтного. Формула по росту/полу
  (`height * 0.415` / `height * 0.413`) — задел на будущую авто-калибровку,
  в MVP не используется и в онбординге не участвует.
- Если платформа отдаёт `DISTANCE_WALKING_RUNNING` / `DISTANCE` — **брать её**,
  она точнее, чем `шаги × длина шага`. Шаги использовать как фолбэк.
- Прогресс **монотонно неубывающий**: назад по маршруту не откатываемся никогда,
  даже если источник данных отдал отрицательную дельту.

### 5.1.1 Только шаги (MVP)

Прогресс двигают только шаги и `DISTANCE_WALKING_RUNNING` с телефона/часов.
Велосипед, бег как отдельная активность, плавание и т.п. — **не учитываются**.
`StepSample.source` перечисляет источники **шагомера** (HealthKit, Health
Connect), не типы активности. Если добавим другие активности — это отдельное
решение с изменением домена, не делать по умолчанию.

### 5.2 Правила учёта

- Работаем с **дельтами**, а не с накопленным итогом: храним `lastSyncedAt` и
  запрашиваем интервал `[lastSyncedAt, now]`.
- При старте квеста начальный `lastSyncedAt` = **начало текущих суток**
  пользователя (00:00 локально), не момент старта. Шаги, сделанные в тот же
  день до старта квеста, тоже засчитываются — считаем по дням, а не с
  точности до секунды старта.
- Запись дельт **идемпотентна**: ключ `(userId, journeyId, intervalStart)`.
  Повторный синк того же интервала не должен удваивать прогресс.
- Границы суток считаются в **локальной таймзоне пользователя**, храним всё в UTC.
- Дедупликация источников: если и HealthKit, и стороннее приложение записали шаги
  за один интервал — берём один источник, приоритет у системного.
- Санитайзер: отсекать интервалы с нереалистичным темпом (> 250 шагов/мин)
  и помечать их флагом вместо тихого отбрасывания.

### 5.3 Производные величины

- **День квеста** = `floor(разница в локальных календарных днях между стартом и сейчас) + 1`.
  Считать по календарным датам, **не** делением миллисекунд на 86400000.
- **Темп** = скользящее среднее метров/день за последние 7 календарных дней;
  если данных меньше 3 дней — берём среднее за всё время квеста.
- **ETA (Estimated Arrival)** = `now + (remainingMeters / темп)` дней.
  Если темп нулевой — показываем прочерк, а не бесконечность.
- **Дельта друга** = `друг.метры - мой.метры`, показывается со знаком: `+229 км`.

### 5.4 Формат чисел

Единый форматтер в `core/formatters.dart`, повторяет референс:

- `< 1 000 м` → целые метры: `196 meters`
- `1 км … 100 км` → два знака: `5.23 kilometers`
- `> 100 км` → целые: `2853 kilometers`
- Подпись единиц — отдельной строкой, мелким шрифтом, под числом.
- В домене — всегда **метры, целые числа**. Форматирование только в presentation.
- **Только метрическая система.** Миль нет и не планируется — в §6.5
  переключателя единиц не будет, убирать из UI/настроек нечего проектировать.

## 6. Экраны

Внизу — **пять вкладок**: Путь · Карта · Трофеи · Друзья · Настройки.
Иконки в едином линейном золотом стиле, активная подсвечена.

### 6.1 Вкладка «Путь» — главный экран (Flame)

Центральный экран приложения.

**Поведение:** экран — это **горизонтальная лента вдоль всего маршрута**.
Пользователь скроллит её пальцем, и по мере скролла **меняется картинка**:
слои пейзажа, регион, строка нарратива и цифра расстояния соответствуют той
позиции маршрута, на которую он сейчас смотрит.

- Скролл **свободный** — можно отмотать назад к пройденному и заглянуть вперёд.
- Слои двигаются с разной скоростью (`ParallaxComponent`, разные
  `velocityMultiplier`): небо почти статично, дальние холмы медленно, передний
  план быстро.
- Внизу — два якоря: **`< Start`** (в начало маршрута) и **`You >`**
  (к текущей позиции игрока). Прыжок анимированный, не мгновенный.
- **Фигурка путника** отрисована в позиции `You`. При скролле в другую часть
  маршрута фигурки в кадре нет — там просто пейзаж.
- При появлении новых шагов позиция `You` **плавно интерполируется**
  (`Tween` / `lerp` за ~800–1200 мс), не прыгает рывком. Если пользователь
  сейчас смотрит на `You`, камера едет вместе с ним.
- Цифры и подписи под сценой обновляются в такт скроллу: `День N`, расстояние,
  название региона, строка нарратива курсивом.

**Небо** — процедурный градиент по **реальному времени суток** пользователя:
ночь со звёздами, рассвет, день, закат. Звёзды — отдельный слой с
прозрачностью, привязанной к фазе.

**Ландшафт** — набор силуэтных слоёв по биомам (равнина → лес → горы → пустошь),
комбинируются по позиции. Палитра слоёв тоже сдвигается по времени суток.

Требования: **60 fps** на среднем железе, отсутствие джанка при появлении
оверлеев. Игровой цикл **паузим**, когда экран не виден.

#### Завершение квеста

Когда `progress.meters >= journey.totalMeters`:

1. Полноэкранный **экран награды**: пройденный маршрут, дни в пути, общая
   дистанция, разблокированные трофеи (§6.3). Не блокирует навигацию —
   пользователь может его закрыть.
2. Вкладка «Путь» переходит в состояние **«Квест завершён»**: сцена статична
   на финальном виде точки B, вместо прогресса — призыв вернуться в каталог
   квестов.
3. **Новый квест не стартует автоматически.** Пользователь идёт в экран
   выбора квеста (тот же каталог, что на онбординге, и в Настройки → «Смена
   квеста», §6.5) — пройденный квест там помечен как **завершён** (бейдж/
   галочка), но остаётся в списке, не исчезает. Пока в каталоге **один
   квест** (§8, §14) — после завершения экран выбора по сути пуст, кроме
   этой одной завершённой карточки; это ожидаемое состояние MVP, не баг.
4. Шаги, накопленные после завершения (пока не выбран новый квест), **не
   теряются**: копятся как непривязанный буфер и зачисляются в прогресс
   нового квеста при его выборе — так же, как обычная дельта.

### 6.2 Вкладка «Карта» — Quest Stats

Шапка со статистикой квеста:

- Общая длина маршрута крупно золотом + «To \<точка B\>».
- `Quest Started` — дата старта.
- `Estimated Arrival` — расчётный ETA (§5.3).

Ниже — **рисованная карта маршрута**:

- Один заранее нарисованный ассет на квест (`assets/journeys/{id}/map.webp`),
  стиль — чернильная иллюстрация. Растр WebP, ~4096 px по длинной стороне,
  с mip-уровнями. SVG — только если арт изначально векторный.
- Путь задан **полилинией в нормализованных координатах** `(0..1, 0..1)` поверх
  картинки, в `map.json`, вместе с накопленным расстоянием в каждой вершине.
  Отсюда: `метры → точка на карте` и обратно.
- Пройденный участок выделен цветом, непройденный — пунктир.
- Ориентиры (`Landmark`) нарисованы прямо в ассете; интерактивные хотспоты
  лежат в `map.json`. Закрытые до подхода игрока — приглушены.
- **Пины друзей** цветные, поверх карты; в списке под картой — имя, цвет пина
  и дельта относительно вас (`+229 km`).
- Пан и зум — `InteractiveViewer`. Никаких сетевых тайлов, экран **полностью
  офлайновый**.
- Кнопка `Challengers` ведёт на вкладку друзей.

### 6.3 Вкладка «Трофеи»

- Сетка достижений: пройденные дистанции, серии дней, достигнутые ориентиры,
  обгон друга.
- Полученные — золотом, неполученные — силуэтом с прогресс-подписью
  («осталось 40 км»).
- Условия достижений — **данные, а не код**: описываются в конфиге и
  проверяются одним чистым evaluator'ом в `domain/`.

### 6.4 Вкладка «Друзья» — Challengers

- Таблица: цвет пина, аватар, ник, прогресс (метры + %), дельта относительно вас.
- Собственная строка **всегда закреплена** и визуально выделена.
- Сортировка по прогрессу; переключатель периода (день / неделя / всё время).
- Добавление друга: по нику или ссылке-приглашению (deep link).
- Заявка требует **взаимного подтверждения**. До подтверждения прогресс не виден.
- Цвет пина друга стабилен: назначается один раз и совпадает на карте и в таблице.
- **Только пассивное сравнение.** Групповых квестов, общих маршрутов на
  несколько человек и соревнований в MVP нет — каждый идёт свой квест в своём
  темпе, друзья видны в таблице и на карте. Не проектировать сущность
  «команда/party» заранее.

### 6.5 Вкладка «Настройки»

Профиль, длина шага, приватность, разрешения, язык, смена квеста. Единиц
измерения в настройках нет — только метрическая система (§5.4).

## 7. Разрешения и приватность

- Запрашивать доступ к здоровью **не на старте**, а в момент, когда пользователь
  начинает квест, с экраном-объяснением «зачем».
- iOS: `NSHealthShareUsageDescription` в `Info.plist`. Приложение только
  **читает** данные, писать в HealthKit не нужно.
- Android: Health Connect, разрешения `READ_STEPS`, `READ_DISTANCE`;
  фоновое чтение — `READ_HEALTH_DATA_IN_BACKGROUND`.
- Health Connect может быть **не установлен** на устройстве — обработать этот
  случай явно, с диплинком в Play Store.
- Отказ в разрешении — **не тупик**: приложение работает, показывает состояние
  «нет данных о шагах» и кнопку перезапроса.
- Друзьям уходит **только агрегированный прогресс** по квесту. Сырые
  health-данные, геолокация и любые медицинские метрики **никогда** не покидают
  устройство и не пишутся в Firestore.
- Пользователь может скрыть свой прогресс от конкретного друга.
- **Фоновый синк — включён.** `READ_HEALTH_DATA_IN_BACKGROUND` используется по
  назначению: приложение синкает шаги не только при открытии, а периодически
  в фоне, чтобы прогресс друзей на карте и пуши о них не отставали на сутки.
  Механизм фонового запуска — **отдельное архитектурное решение, требует
  плана** по правилу §13 (новая зависимость + разрешения); не начинать писать
  код фонового синка без плана. Предпочтительное направление (проверить в
  плане, не считать финальным): **event-driven background delivery**
  HealthKit — iOS сам уведомляет приложение при изменении данных, точнее и
  экономичнее по батарее, чем периодический опрос. `workmanager`/
  `BGTaskScheduler`-подобный поллинг — фолбэк там, где push-подобного API нет
  (в т.ч. часть сценариев на Android).
- **Пуш-уведомления — включены широко**, не только «друг обогнал вас»: везде,
  где событие в квесте касается пользователя (друг дошёл до ориентира, друг
  обогнал, возможно — свои вехи). Точный список событий уточняется на Phase 9
  (`docs/implementation-plan.md`), сама категория «пуши нужны» — решена.
  Разрешение на пуши (iOS opt-in, Android 13+ `POST_NOTIFICATIONS`) — отдельный
  запрос, не часть health-онбординга.
- **Постоянное отображение прогресса на заблокированном экране** — отдельная
  фича сверх пуш-уведомлений: постоянное уведомление с текущим прогрессом,
  видимое и в шторке, и на экране блокировки. **Android реализован**
  («Решено 2026-08-24» выше, `docs/screens/lock-screen.md`) —
  `flutter_local_notifications` (уведомление) + `workmanager` (фоновый
  синк), обе зависимости в §3. iOS (Live Activity) остаётся отдельным
  follow-up: по §13 нужен план и согласование `live_activities` (или
  аналога) и минимальной версии iOS до реализации. **Важно для оценки
  трудозатрат:** Live Activity на iOS даже через Flutter-плагин требует
  нативного **Widget Extension на Swift** — это не «просто добавить
  пакет», содержательный нативный код; плюс сама фича на iOS начинается с
  16.1+, деградация на более старых iOS (минимум приложения — iOS 15 по
  Flutter 3.47) должна быть предусмотрена в плане.

## 8. Данные и бэкенд

**Офлайн-first.** Источник правды на устройстве — drift (SQLite). Firestore —
слой синхронизации, не единственное хранилище. Приложение обязано полностью
работать без сети: и главный экран, и карта, и трофеи.

**Аутентификация:** Firebase Auth, **анонимный вход по умолчанию** — квест
идётся без регистрации, аккаунт создаётся автоматически при первом запуске
(`signInAnonymously`). Постоянный логин (email/Google/Apple — выбор провайдера
не сделан, не блокирует MVP) добавляется **позже** как апгрейд анонимной
сессии (`linkWithCredential`), когда пользователь идёт добавлять друзей — без
него сущность `Friendship` бессмысленна (нужен стабильный идентификатор,
переживающий переустановку). Не проектировать экран логина в MVP, но не
блокировать анонимный `uid` от будущей привязки.

**Мультиустройство и офлайн-мердж:** прогресс синкается **аддитивно** через
уже существующий идемпотентный ключ дельты `(userId, journeyId,
intervalStart)` (§5.2) — отдельного «чей прогресс главнее» решения не нужно.
Онлайн: локальная дельта пишется в drift и сразу отправляется в Firestore.
Офлайн: дельта копится в локальной очереди на устройстве и досылается в
Firestore при восстановлении сети — сервер получает те же дельты, что и был
бы получены онлайн, просто позже; повторная отправка безопасна благодаря
идемпотентности. Если один и тот же интервал синкнут с двух устройств одного
аккаунта — дедуп §5.2 (приоритет системного источника) применяется как обычно.

Схема Firestore (черновик):

```
users/{uid}                       # ник, аватар, настройки приватности
users/{uid}/progress/{journeyId}  # метры, дата старта, обновлено, текущий квест
friendships/{pairId}              # отсортированная пара uid, статус, кто инициатор
journeys/{journeyId}              # каталог квестов (read-only для клиента)
```

- Каталог квестов — метаданные в Firestore, тяжёлые ассеты (карта, слои) в
  Firebase Storage, кэшируются на устройстве после первой загрузки.
- **Квесты только из каталога.** Пользователь не собирает свой маршрут (не
  задаёт длину, не выбирает биомы) — `journeys/{journeyId}` полностью
  редакторский контент, для клиента read-only. Конструктор маршрутов —
  возможное развитие, не MVP.
- Прогресс пишется **батчами** (не чаще раза в несколько минут), не на каждый
  тик шагомера.
- Security Rules обязательны: читать чужой прогресс можно **только** при
  `accepted`-дружбе. Правила покрываются тестами эмулятора.
- Cloud Functions — для пушей (друг обогнал вас, друг дошёл до ориентира) и
  агрегаций.

## 9. Дизайн-система

Живёт в `lib/design/`. Никаких цветов и размеров по месту в виджетах.

- **Фон:** почти чёрный `#000000` … `#0B0B0D`; карточки/шапки `#1B1B1E`.
- **Акцент:** тёплое золото ≈ `#E0AE3F`. Им — цифры, активные иконки, кнопки.
- **Текст:** приглушённый белый `#EDE7DA`, вторичный — 60 % прозрачности.
- **Шрифт:** антиквенный serif с фэнтезийным характером для заголовков и цифр;
  нарратив — тот же serif курсивом. Один шрифт на всё приложение.
  **Лицензия — только общественное достояние / свободная (OFL и т.п.), без
  платных лицензий на встраивание.** Конкретное семейство ещё не выбрано —
  подбирается на Phase 1 (design system), не блокирует старт разработки;
  кандидаты — цифровые переиздания исторических шрифтов под OFL (например, в
  духе Fell Types). Перед подключением — проверить лицензию файла шрифта так
  же, как §1.1 требует проверять охрану сеттинга: «шрифт выглядит старым» не
  равно «шрифт свободен».
- **Иконки:** тонкие линейные, золотые, единая толщина штриха.
- **Арт:** силуэты сплошной заливкой, без градиентов внутри объектов; градиент
  только в небе. Слои различаются светлотой, а не деталями.
- Тёмная тема — единственная. Светлой нет.

### 9.1 Ассеты арта — TODO: источник не выбран

Источник арта (заказная иллюстрация / генерация / готовые ассет-паки) пока не
решён — лежит в `assets/journeys/{journeyId}/` (§4) как папка, которую
наполняем вручную. Что понадобится **вне зависимости** от источника, когда
источник выберем:

- **Слои параллакса** (`segments/`): силуэтная заливка, без внутренних
  градиентов, отдельный файл на слой (небо/дальний план/средний план/передний
  план), совпадающая палитра в рамках биома, **бесшовное зацикливание по
  горизонтали** (правый край стыкуется с левым) — иначе `ParallaxComponent`
  даст видимый шов при долгом скролле одного биома.
- **Карта квеста** (`map.webp`): единая иллюстрация ~4096 px по длинной
  стороне, чернильный стиль, ориентиры прорисованы прямо в ассете — координаты
  хотспотов под них берутся из `map.json` уже после того как картинка готова.
- **Палитра и толщина линий** — из этого раздела (§9), не по вкусу
  исполнителя/промпта на каждый квест отдельно, иначе квесты визуально
  разъедутся между собой.
- Нарратив (`NarrativeBeat`) пишется человеком вручную (§5, §11) — не зависит
  от решения по визуальному арту, можно делать параллельно.

Пока источник не выбран — **не проектировать** пайплайн генерации/приёмки
арта в коде; просто следовать структуре папок из §4.

  идемпотентный ключ дельты; онлайн пишем сразу в Firebase, офлайн — копим

- **Постоянное отображение на экране блокировки — Android реализован.**
