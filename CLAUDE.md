## 1. О проекте

**There and Back** — мобильное приложение-«путешествие на шагах».

Пользователь выбирает маршрут (путь из точки **A** в точку **B**). Реальные шаги,
снятые с датчиков телефона, конвертируются в пройденное расстояние и **двигают
фигурку игрока по маршруту**. Цель — дойти до точки B.

Ключевая метафора: приложение не про фитнес-метрики, а про **прогресс в пути**.
Пользователю показывают не «8412 шагов», а «День 5, 5.23 километра, Halfling
Country, перешёл ручей по узкому мостику». Числа в UI всегда завёрнуты в язык
путешествия.

Социальная часть: пользователь добавляет друзей и видит, кто где идёт по тому же
маршруту — на карте пинами и в таблице.

### 1.1 Сеттинг

Референсные скриншоты (см. §2.1) взяты из приложения с тонко замаскированным
толкиновским сеттингом («Mount Fire», «Halfling Country», «Mr Underhill»). Мы
копируем **структуру и UX**, но не сеттинг — свои имена и география (§2.2).

Первый квест в каталоге — **«The Odyssey: Troy to Ithaca»**
(`assets/journeys/odyssey-ithaca/`, черновик локаций и нарратива —
`journeys/odyssey-ithaca/locations.json` в рабочих материалах). Остальные
квесты каталога — собственный фэнтези-мир; название мира и регионов ещё не
придумано (см. §14).

## 2. Референс и UX

### 2.1 Что взято из референса

Разработка ведётся с оглядкой на скриншоты-референс, которые задают направление:

- Тёмная тема, почти чёрный фон, **золотой акцент** и антиквенный serif-шрифт.
- Главный экран — **силуэтный пейзаж**: чёрный передний план, цветные слои
  холмов, градиентное небо, маленькая фигурка путника с посохом.
- Крупные цифры расстояния золотом, под ними — регион и одна строка нарратива
  курсивом.
- Счётчик «День N» от старта квеста.
- Экран статистики — **рисованная карта** в стиле чернильной иллюстрации:
  пунктирная тропа, нарисованные ориентиры, цветные пины друзей.
- Пять вкладок внизу.

### 2.2 Чего в референсе нет и что мы делаем иначе

- Свой сеттинг и свои названия (§1.1).
- Нормальная работа офлайн и внятная обработка отказа в разрешениях (§7).

## 3. Платформы и стек

| Слой | Выбор |
|---|---|
| Платформы | iOS и Android, одна кодовая база |
| Framework | **Flutter** (stable, ≥ 3.47 / Dart ≥ 3.13) |
| Язык | Dart |
| Сцена главного экрана | **Flame** (`flame` ^1.38) — `ParallaxComponent` |
| Состояние | **Riverpod** (`flutter_riverpod` + `riverpod_generator`) |
| Модели / DTO | `freezed` + `json_serializable` |
| Навигация | `go_router` |
| Локальное хранилище | `drift` (SQLite) — источник правды офлайн |
| Шаги | `health` (^13.x) — Health Connect на Android. iOS **временно** на Core Motion (`CMPedometer`) через свой `MethodChannel`, не на HealthKit из `health` — см. «Почему так» и §14 |
| Карта | **своя рисованная иллюстрация**, `InteractiveViewer` (см. §6.2) |
| Бэкенд | **Firebase**: Auth, Cloud Firestore, Cloud Functions, FCM |
| Аналитика/краши | Firebase Analytics + Crashlytics |
| Тесты | `flutter_test`, `mocktail`, `integration_test` |
| Лок-скрин уведомление (Android) | `flutter_local_notifications` (§7, `docs/screens/lock-screen.md`) |
| Фоновый синк (Android) | `workmanager` (§7, `docs/screens/lock-screen.md`) |
| Фоновая музыка | `audioplayers` (^6.x) (§6.5, §14) |

### Почему так

- **Flutter, а не React Native** — главный экран это анимированная сцена с
  постоянной перерисовкой. Flutter рисует всё сам через Impeller, кадры
  стабильнее. Плюс `health` даёт **единый API** поверх HealthKit и Health
  Connect; в RN пришлось бы держать две разные библиотеки и писать обёртку
  вручную.
- **Flame, а не самописный `CustomPainter`** — `ParallaxComponent` уже умеет
  многослойный фон с разными скоростями, бесшовное зацикливание и корректный
  game loop. Не изобретать заново.
- **Никакого `flutter_map` / OSM / Google Maps.** Карта — вымышленный мир,
  тайлы реальной планеты не нужны. Это минус тяжёлая зависимость, минус сетевые
  запросы, и офлайн-работа получается бесплатно.
- **Health Connect, не Google Fit** — Google Fit API устарел (регистрация новых
  приложений закрыта с 1 мая 2024), в `health` его поддержка удалена начиная с
  версии 11.0.0. **Никогда не предлагать Google Fit.**
- **iOS временно на Core Motion (`CMPedometer`), не на HealthKit — явный,
  осознанный отход от «единого API» выше, по прямому запросу (2026-08-28,
  §14).** HealthKit — Apple capability, требующая платного Apple Developer
  Program аккаунта даже для локальной сборки на свой телефон; Core Motion —
  обычное runtime-разрешение (`NSMotionUsageDescription`), работает с
  бесплатным Personal Team. Доступ — через **свой `MethodChannel`**
  (`ios/Runner/AppDelegate.swift` ↔ `ios_pedometer_channel.dart`), не через
  пакет `cm_pedometer`: тот единственный существующий пакет-обёртка над
  `CMPedometer.queryPedometerData(from:to:)` ломает `flutter pub get` для
  любого проекта, который на него подписан (битая Android-регистрация
  плагина — `androidPackage` указывает на несуществующий класс), даже если
  Android его вообще не использует (§14, обнаружено в CI). Плата за
  Core Motion в любом случае: только шаги этого iPhone (без агрегации с
  Apple Watch), дистанция — оценка Core Motion, а не HealthKit-агрегат.
  Считать временным решением — TODO на миграцию обратно на HealthKit лежит
  в `ios_step_counting_service.dart` и в §14; ради него
  `AndroidStepCountingService` и `IosStepCountingService` за одним
  интерфейсом `StepCountingService` специально разведены по независимым
  классам (§14, 2026-08-28).
- **Firebase** — Auth + Firestore + FCM закрывают друзей, синк и пуши в MVP без
  своего сервера.
- **`audioplayers`, а не самописный канал** — ничего в стеке до этого не
  проигрывало звук; `audioplayers` — стандартный кросс-платформенный пакет
  именно под эту задачу (луп локального ассета из `assets/`, `flutter`/`dart`
  без нативного кода с обеих сторон), заметно проще `just_audio` для этого
  MVP, которому не нужны ни фоновое воспроизведение (§6.5 — трек играет только
  пока приложение открыто), ни стриминг. Никаких новых Android/iOS-разрешений
  не требует — локальное воспроизведение файла из ассетов не капability и не
  runtime-permission ни на одной платформе.

## 4. Архитектура

**Feature-first**, три слоя внутри каждой фичи.

```
lib/
  main.dart
  app/                 # роутер, тема, DI-корень, bootstrap
  core/                # общее: ошибки, форматтеры, extensions, константы
  design/              # дизайн-система: цвета, типографика, компоненты
  data/                # drift-схема, Firestore-репозитории, health-адаптеры
  features/
    journey/           # маршрут, прогресс, главный экран
      domain/          # сущности + чистые функции, БЕЗ Flutter-импортов
      data/            # репозитории, мапперы
      presentation/    # виджеты, Flame-компоненты, Riverpod-провайдеры
    steps/             # чтение шагов, синхронизация, дельты
    quest_map/         # рисованная карта, статистика квеста, ETA
    achievements/      # трофеи
    friends/           # друзья, таблица прогресса
    profile/           # настройки
  l10n/                # локализация (ru, en)
assets/
  journeys/{journeyId}/
    map.webp           # рисованная карта маршрута
    map.json           # путь, ориентиры, привязка к прогрессу
    segments/          # слои пейзажа по сегментам
```

Правила слоёв:

- `domain/` не импортирует `package:flutter/*`, Firebase и `health`. Только
  чистый Dart. Вся математика прогресса живёт здесь и покрыта unit-тестами.
- UI никогда не ходит в репозиторий напрямую — только через Riverpod-провайдер.
- Firestore-модели и доменные сущности **разные типы**. Маппинг в `data/`.

```dart

Segment       // участок маршрута: диапазон [fromMeters, toMeters], регион, биом, набор слоёв
```

### 5.1 Шаги → расстояние

Единственное место конвертации — `features/journey/domain/stride.dart`.

- **Онбординг ничего не спрашивает про длину шага.** Дефолт для всех —
  **0.75 м**, без вопросов про рост и пол. Точность калибруется позже.
- Пользователь может задать длину шага вручную в профиле (§6.5) — ручное
  значение всегда приоритетнее дефолтного. Формула по росту/полу
  (`height * 0.415` / `height * 0.413`) — задел на будущую авто-калибровку,
  в MVP не используется и в онбординге не участвует.
- Если платформа отдаёт `DISTANCE_WALKING_RUNNING` / `DISTANCE` — **брать её**,
  она точнее, чем `шаги × длина шага`. Шаги использовать как фолбэк.
- Прогресс **монотонно неубывающий**: назад по маршруту не откатываемся никогда,
  даже если источник данных отдал отрицательную дельту.

### 5.1.1 Только шаги (MVP)

Прогресс двигают только шаги и `DISTANCE_WALKING_RUNNING` с телефона/часов.
Велосипед, бег как отдельная активность, плавание и т.п. — **не учитываются**.
`StepSample.source` перечисляет источники **шагомера** (HealthKit, Health
Connect), не типы активности. Если добавим другие активности — это отдельное
решение с изменением домена, не делать по умолчанию.

### 5.2 Правила учёта

- Работаем с **дельтами**, а не с накопленным итогом: храним `lastSyncedAt` и
  запрашиваем интервал `[lastSyncedAt, now]`.
- При старте квеста начальный `lastSyncedAt` = **точный момент старта**
  (когда пользователь нажал «Начать квест»). Шаги, сделанные раньше в этот
  же день, до старта квеста, **не** засчитываются. (Изменено 2026-08-27 —
  раньше был бэкфилл до начала суток, см. §14.)
- Запись дельт **идемпотентна**: ключ `(userId, journeyId, intervalStart)`.
  Повторный синк того же интервала не должен удваивать прогресс.
- Границы суток считаются в **локальной таймзоне пользователя**, храним всё в UTC.
- Дедупликация источников: если и HealthKit, и стороннее приложение записали шаги
  за один интервал — берём один источник, приоритет у системного.
- Санитайзер: отсекать интервалы с нереалистичным темпом (> 250 шагов/мин)
  и помечать их флагом вместо тихого отбрасывания.

### 5.3 Производные величины

- **День квеста** = `floor(разница в локальных календарных днях между стартом и сейчас) + 1`.
  Считать по календарным датам, **не** делением миллисекунд на 86400000.
- **Темп** = скользящее среднее метров/день за последние 7 календарных дней;
  если данных меньше 3 дней — берём среднее за всё время квеста.
- **ETA (Estimated Arrival)** = `now + (remainingMeters / темп)` дней.
  Если темп нулевой — показываем прочерк, а не бесконечность.
- **Дельта друга** = `друг.метры - мой.метры`, показывается со знаком: `+229 км`.

### 5.4 Формат чисел

Единый форматтер в `core/formatters.dart`, повторяет референс:

- `< 1 000 м` → целые метры: `196 meters`
- `1 км … 100 км` → два знака: `5.23 kilometers`
- `> 100 км` → целые: `2853 kilometers`
- Подпись единиц — отдельной строкой, мелким шрифтом, под числом.
- В домене — всегда **метры, целые числа**. Форматирование только в presentation.
- **Только метрическая система.** Миль нет и не планируется — в §6.5
  переключателя единиц не будет, убирать из UI/настроек нечего проектировать.

## 6. Экраны

Внизу — **пять вкладок**: Путь · Карта · Трофеи · Друзья · Настройки.
Иконки в едином линейном золотом стиле, активная подсвечена.

### 6.1 Вкладка «Путь» — главный экран (Flame)

Центральный экран приложения.

**Поведение:** экран — это **горизонтальная лента вдоль всего маршрута**.
Пользователь скроллит её пальцем, и по мере скролла **меняется картинка**:
слои пейзажа, регион, строка нарратива и цифра расстояния соответствуют той
позиции маршрута, на которую он сейчас смотрит.

- Скролл — это **перемотка, не подглядывание вперёд**: назад можно отмотать
  до любого уже пройденного места, вплоть до самого начала маршрута; вперёд —
  **не дальше текущей позиции игрока** (2026-08-30, §14 — пересматривает более
  раннее «и заглянуть вперёд»: смотреть там пока не на что, эта земля ещё не
  пройдена).
- Слои двигаются с разной скоростью (`ParallaxComponent`, разные
  `velocityMultiplier`): небо почти статично, дальние холмы медленно, передний
  план быстро.
- Внизу — два якоря: **`< Start`** (в начало маршрута) и **`You >`**
  (к текущей позиции игрока). Прыжок анимированный, не мгновенный.
- **Сверху слева — кнопка возврата к выбору маршрута** (2026-08-31, §14):
  открывает тот же экран каталога квестов, что и до старта похода, не сбрасывая
  текущий активный квест — это чисто навигационный режим «browsing»
  (`browsingCatalogProvider`), отдельный от `selectedJourneyProvider`. Каждая
  карточка маршрута в каталоге показывает свой собственный процент пройденного
  пути сверху слева (§8) — независимо от того, какой квест сейчас активен.
- **Фигурка путника** в двух видах. На актуальной позиции (`You`) она всегда
  сплошная, золотая: она никуда не уезжает вместе с перемоткой. Пока скролл
  отмотан на пройденное место назад от `You` — на **этой** позиции появляется
  контурная, приглушённая фигурка-тень («был здесь»); она одна двигается при
  перемотке, солидная фигурка на `You` не трогается. На `You` тень не рисуется
  — там уже стоит сама solid-фигурка (2026-08-30, §14).
- При появлении новых шагов позиция `You` **плавно интерполируется**
  (`Tween` / `lerp` за ~800–1200 мс), не прыгает рывком. Если пользователь
  сейчас смотрит на `You`, камера едет вместе с ним.
- **Друзья на этой же ленте** — Настройки → «Друзья на карте» (§6.5,
  2026-08-31, §14), выключено по умолчанию. Включённое — каждый принятый
  друг рисуется той же фигуркой путника, что и сам игрок, но **своим
  стабильным цветом пина** (§6.4's `friendPinPalette`/`pinColorIndexForUid`,
  не золотым) на его собственной позиции по метрам маршрута, и **с ником
  прямо над фигуркой всегда** — здесь, в отличие от вкладки «Карта», это
  не скрывается никаким переключателем.
- Цифры и подписи под сценой обновляются в такт скроллу: `День N`, расстояние,
  название региона, строка нарратива курсивом.

**Небо** — процедурный градиент: ночь со звёздами, рассвет, день, закат.
Звёзды — отдельный слой с прозрачностью, привязанной к фазе. Для квеста,
контент которого задаёт собственную сюжетную шкалу времени (сегодня —
только «Одиссея», через `departureHour`/`durationDays` каждого сегмента
`locations.json`, §14 «Решено 2026-09-03») — фаза берётся из **вымышленного
времени** в той точке маршрута, куда сейчас отмотан скролл сцены «Путь»
(`fictionalHourFor`), а не из часов устройства: в начале маршрута — время
дня, в которое персонаж вышел по сюжету, между именованными точками —
интерполяция, на затяжных по сюжету перегонах — несколько смен дня/ночи
подряд. Длительность каждого сегмента ограничена: не больше 1 вымышленных
суток на каждые 10 000 м сегмента, чтобы обычная прогулка никогда не
пролистывала сразу несколько сюжетных суток. Для любого квеста без такого
контента — прежнее поведение: **реальное время суток** пользователя.

**Ландшафт** — набор силуэтных слоёв по биомам (равнина → лес → горы → пустошь),
комбинируются по позиции. Палитра слоёв тоже сдвигается по времени суток.

Требования: **60 fps** на среднем железе, отсутствие джанка при появлении
оверлеев. Игровой цикл **паузим**, когда экран не виден.

#### Завершение квеста

Когда `progress.meters >= journey.totalMeters`:

1. Полноэкранный **экран награды**: пройденный маршрут, дни в пути, общая
   дистанция, разблокированные трофеи (§6.3). Не блокирует навигацию —
   пользователь может его закрыть.
2. Вкладка «Путь» переходит в состояние **«Квест завершён»**: сцена статична
   на финальном виде точки B, вместо прогресса — призыв вернуться в каталог
   квестов.
3. **Новый квест не стартует автоматически.** Пользователь идёт в экран
   выбора квеста (тот же каталог, что на онбординге, и в Настройки → «Смена
   квеста», §6.5) — пройденный квест там помечен как **завершён** (бейдж/
   галочка), но остаётся в списке, не исчезает. В каталоге теперь **два
   квеста** («Одиссея» и «The Road to the Skyfire», §8, §14, добавлен
   2026-09-05) — завершение одного оставляет второй доступным для старта в
   том же экране, не пустой список; когда квестов было ещё один (более
   ранняя редакция этого пункта), пустой-кроме-одной-карточки экран был
   ожидаемым состоянием MVP, не багом.
4. Шаги, накопленные после завершения (пока не выбран новый квест), **не
   теряются**: копятся как непривязанный буфер и зачисляются в прогресс
   нового квеста при его выборе — так же, как обычная дельта.

### 6.2 Вкладка «Карта» — Quest Stats

Шапка со статистикой квеста:

- Общая длина маршрута крупно золотом + «To \<точка B\>».
- `Quest Started` — дата старта.
- `Estimated Arrival` — расчётный ETA (§5.3).

Ниже — **рисованная карта маршрута**:

- Один заранее нарисованный ассет на квест (`assets/journeys/{id}/map.webp`),
  стиль — чернильная иллюстрация. Растр WebP, ~4096 px по длинной стороне,
  с mip-уровнями. SVG — только если арт изначально векторный.
- Путь задан **полилинией в нормализованных координатах** `(0..1, 0..1)` поверх
  картинки, в `map.json`, вместе с накопленным расстоянием в каждой вершине.
  Отсюда: `метры → точка на карте` и обратно.
- Пройденный участок выделен цветом, непройденный — пунктир.
- Ориентиры (`Landmark`) нарисованы прямо в ассете; интерактивные хотспоты
  лежат в `map.json`. Закрытые до подхода игрока — приглушены.
- **Трофеев на карте нет** — были показаны над своей точкой на маршруте с
  пунктирной линией-указателем (2026-08-30), но убраны отдельным styling-
  решением: дублировали вкладку «Трофеи» (§6.3), не тапабельны на карте, и
  на нарисованной иллюстрации читались как визуальный шум. Своя точка на
  маршруте у трофея по-прежнему есть (та же `metersToPoint`) — просто больше
  не отрисовывается здесь; полный набор трофеев и их статус — только на
  вкладке «Трофеи» (§6.3).
- **Друзья на карте** — Настройки → «Друзья на карте» (§6.5, 2026-08-31,
  §14), выключено по умолчанию, тот же переключатель, что и на вкладке
  «Путь». Включённое — каждый принятый друг рисуется тем же силуэтом
  шлема, что и позиция самого игрока, но своим стабильным цветом пина
  (`friendPinPalette`/`pinColorIndexForUid`, §6.4) вместо золотого.
- **По умолчанию на карте видны только шлемы** (2026-08-31, §14, по
  прямому запросу) — подписи ориентиров и их иконки скрыты, пока не
  включена **легенда карты**: маленький переключатель снизу справа под
  картой. Включённая легенда возвращает иконки ориентиров (кликабельные,
  как раньше) и добавляет ник над каждым шлемом друга — на этой вкладке,
  в отличие от «Путь», ник друга не показывается без легенды. Шлем самого
  игрока и шлемы друзей рисуются всегда, независимо от легенды — легенда
  касается только подписей и иконок ориентиров.
- Пан и зум — `InteractiveViewer`. Никаких сетевых тайлов, экран **полностью
  офлайновый**.

## 7. Разрешения и приватность

- Запрашивать доступ к здоровью **не на старте**, а в момент, когда пользователь
  начинает квест, с экраном-объяснением «зачем».
- iOS: `NSHealthShareUsageDescription` в `Info.plist`. Приложение только
  **читает** данные, писать в HealthKit не нужно.
- Android: Health Connect, разрешения `READ_STEPS`, `READ_DISTANCE`;
  фоновое чтение — `READ_HEALTH_DATA_IN_BACKGROUND`.
- Health Connect может быть **не установлен** на устройстве — обработать этот
  случай явно, с диплинком в Play Store.
- Отказ в разрешении — **не тупик**: приложение работает, показывает состояние
  «нет данных о шагах» и кнопку перезапроса.
- Друзьям уходит **только агрегированный прогресс** по квесту. Сырые
  health-данные, геолокация и любые медицинские метрики **никогда** не покидают
  устройство и не пишутся в Firestore.
- Пользователь может скрыть свой прогресс от конкретного друга.
- **Фоновый синк — включён.** `READ_HEALTH_DATA_IN_BACKGROUND` используется по
  назначению: приложение синкает шаги не только при открытии, а периодически
  в фоне, чтобы прогресс друзей на карте и пуши о них не отставали на сутки.
  Механизм фонового запуска — **отдельное архитектурное решение, требует
  плана** по правилу §13 (новая зависимость + разрешения); не начинать писать
  код фонового синка без плана. Предпочтительное направление (проверить в
  плане, не считать финальным): **event-driven background delivery**
  HealthKit — iOS сам уведомляет приложение при изменении данных, точнее и
  экономичнее по батарее, чем периодический опрос. `workmanager`/
  `BGTaskScheduler`-подобный поллинг — фолбэк там, где push-подобного API нет
  (в т.ч. часть сценариев на Android).
- **Пуш-уведомления — включены широко**, не только «друг обогнал вас»: везде,
  где событие в квесте касается пользователя (друг дошёл до ориентира, друг
  обогнал, возможно — свои вехи). Точный список событий уточняется на Phase 9
  (`docs/implementation-plan.md`), сама категория «пуши нужны» — решена.
  Разрешение на пуши (iOS opt-in, Android 13+ `POST_NOTIFICATIONS`) — отдельный
  запрос, не часть health-онбординга.
- **Постоянное отображение прогресса на заблокированном экране** — отдельная
  фича сверх пуш-уведомлений: постоянное уведомление с текущим прогрессом,
  видимое и в шторке, и на экране блокировки. **Android реализован**
  («Решено 2026-08-24» выше, `docs/screens/lock-screen.md`) —
  `flutter_local_notifications` (уведомление) + `workmanager` (фоновый
  синк), обе зависимости в §3. iOS (Live Activity) остаётся отдельным
  follow-up: по §13 нужен план и согласование `live_activities` (или
  аналога) и минимальной версии iOS до реализации. **Важно для оценки
  трудозатрат:** Live Activity на iOS даже через Flutter-плагин требует
  нативного **Widget Extension на Swift** — это не «просто добавить
  пакет», содержательный нативный код; плюс сама фича на iOS начинается с
  16.1+, деградация на более старых iOS (минимум приложения — iOS 15 по
  Flutter 3.47) должна быть предусмотрена в плане.

## 8. Данные и бэкенд

**Офлайн-first.** Источник правды на устройстве — drift (SQLite). Firestore —
слой синхронизации, не единственное хранилище. Приложение обязано полностью
работать без сети: и главный экран, и карта, и трофеи.

**Аутентификация:** Firebase Auth, **анонимный вход по умолчанию** — квест
идётся без регистрации, аккаунт создаётся автоматически при первом запуске
(`signInAnonymously`). Постоянный логин (email/Google/Apple — выбор провайдера
не сделан, не блокирует MVP) добавляется **позже** как апгрейд анонимной
сессии (`linkWithCredential`), когда пользователь идёт добавлять друзей — без
него сущность `Friendship` бессмысленна (нужен стабильный идентификатор,
переживающий переустановку). Не проектировать экран логина в MVP, но не
блокировать анонимный `uid` от будущей привязки.

**Мультиустройство и офлайн-мердж:** прогресс синкается **аддитивно** через
уже существующий идемпотентный ключ дельты `(userId, journeyId,
intervalStart)` (§5.2) — отдельного «чей прогресс главнее» решения не нужно.
Онлайн: локальная дельта пишется в drift и сразу отправляется в Firestore.
Офлайн: дельта копится в локальной очереди на устройстве и досылается в
Firestore при восстановлении сети — сервер получает те же дельты, что и был
бы получены онлайн, просто позже; повторная отправка безопасна благодаря
идемпотентности. Если один и тот же интервал синкнут с двух устройств одного
аккаунта — дедуп §5.2 (приоритет системного источника) применяется как обычно.

Схема Firestore (черновик):

```
users/{uid}                       # ник, аватар, настройки приватности
users/{uid}/progress/{journeyId}  # метры, дата старта, обновлено, текущий квест
friendships/{pairId}              # отсортированная пара uid, статус, кто инициатор
journeys/{journeyId}              # каталог квестов (read-only для клиента)
```

- Каталог квестов — метаданные в Firestore, тяжёлые ассеты (карта, слои) в
  Firebase Storage, кэшируются на устройстве после первой загрузки.
- **Квесты только из каталога.** Пользователь не собирает свой маршрут (не
  задаёт длину, не выбирает биомы) — `journeys/{journeyId}` полностью
  редакторский контент, для клиента read-only. Конструктор маршрутов —
  возможное развитие, не MVP.
- Прогресс пишется **батчами** (не чаще раза в несколько минут), не на каждый
  тик шагомера.
- Security Rules обязательны: читать чужой прогресс можно **только** при
  `accepted`-дружбе. Правила покрываются тестами эмулятора.
- Cloud Functions — для пушей (друг обогнал вас, друг дошёл до ориентира) и
  агрегаций.

  буквально: та же гарнитура и для обычного UI-текста (label/body), не

### 9.1 Ассеты арта — TODO: источник не выбран

Источник арта (заказная иллюстрация / генерация / готовые ассет-паки) пока не

- **Слои параллакса** (`segments/`): силуэтная заливка, без внутренних

- **Карта квеста** (`map.webp`): единая иллюстрация ~4096 px по длинной

- **Палитра и толщина линий** — из этого раздела (§9), не по вкусу
  исполнителя/промпта на каждый квест отдельно, иначе квесты визуально
  разъедутся между собой.
- Нарратив (`NarrativeBeat`) пишется человеком вручную (§5, §11) — не зависит
  от решения по визуальному арту, можно делать параллельно.

Пока источник не выбран — **не проектировать** пайплайн генерации/приёмки
арта в коде; просто следовать структуре папок из §4.

### 11.1 Версионирование до релиза

Единственный источник версии — поле `version:` в `pubspec.yaml`
(`MAJOR.MINOR.PATCH+BUILD`). Ни в `build.gradle.kts`, ни в `Info.plist`, ни в
коде версию не дублировать — платформы читают её из pubspec.

Текущая версия — **0.0.1+1**. До первого публичного релиза в сторах мажор
остаётся **0**.

Как поднимать (пока мажор — 0):

| Что произошло | Что поднимаем | Пример |
|---|---|---|
| Обычная работа внутри PR: коммиты, пока PR ещё не создан/не готов | ничего | `0.1.1+1` |
| **Создаётся PR** (готов к ревью/мерджу) | `PATCH`, по умолчанию `+0.0.1` | `0.1.1` → `0.1.2` |
| Завершена **фаза** из `docs/implementation-plan.md` (Phase 0–12) | `PATCH` | `0.0.1` → `0.0.2` |
| Завершён **майлстоун** M1–M4 | `MINOR`, `PATCH` → 0 | `0.0.7` → `0.1.0` |
| Сборка отдаётся наружу (TestFlight / internal track / APK тестировщику) | `+BUILD` +1 | `0.1.0+3` → `0.1.0+4` |
| Первый публичный релиз в сторах | `1.0.0` | только по явному решению |

Правила:

- **На каждый создаваемый PR — bump версии**, по умолчанию `PATCH` (`+0.0.1`),
  даже если внутри PR только багфикс/рефакторинг/доки без завершения фазы —
  версия должна расти на каждом PR, а не только на вехах. Если этот же PR
  ещё и закрывает фазу/майлстоун — bump один, по большей из подходящих строк
  таблицы (`MINOR` перекрывает `PATCH`), а не оба подряд.
- **`BUILD` монотонно растёт и никогда не сбрасывается** — даже когда меняется
  `MAJOR.MINOR.PATCH`. Сторы не принимают повторный номер сборки.
- Претендент на релиз до 1.0.0 маркируется **только номером сборки**
  (`0.4.0+12`), суффиксы вида `-beta`/`-rc` не используем: `pubspec` отдаёт их
  в нативные версии платформ, где они ломают сравнение версий.
- Версию поднимаем **отдельным коммитом** `chore: bump version to X.Y.Z+N`,
  не смешивая с фичей — так по истории видно, что вошло в сборку.
- Claude поднимает `PATCH` и `BUILD` сам по таблице выше. `MINOR`, и тем более

Решено 2026-08-30 (§6.1, пересматривает «и заглянуть вперёд» из более раннего
черновика §6.1):

- **Скролл вкладки «Путь» — перемотка назад, не подглядывание вперёд.**
  Вперёд отматывать можно только до текущей позиции игрока (`progressMeters`)
  — дальше по маршруту ещё ничего не пройдено, там нечего показывать. Назад —
  без ограничений, до самого начала маршрута (0 м). Причина пересмотра —
  явный запрос: раньше скролл был свободным в обе стороны.
- **Два вида фигурки путника.** Сплошная золотая — только на настоящей
  позиции игрока (`You`), в мировых координатах маршрута, как и маркеры
  ориентиров/трофеев: она не следует за перемоткой, только видимо съезжает к
  краю экрана, когда экран отмотан в сторону. Приглушённая контурная
  фигурка-«тень» появляется вместо неё в той точке маршрута, на которую сейчас
  отмотан экран (всегда по центру экрана, раз это и есть то, что "сейчас
  смотрим") — показывает "где он был". На `You` тень не рисуется — там уже
  стоит сплошная фигурка, дублировать нечего.
  Реализовано в placeholder-сцене `journey_path_view.dart`'s
  `_TravelerMarker` (солидная версия — `solid: true`, тень — `solid: false`)
  — тот же плейсхолдер `CustomPaint`, что и до Phase 5's настоящей Flame-сцены
  (`flame-scene` скилл), не новый слой поверх него.
- **Пока экран смотрит на `You`, он едет за прогрессом сам.** Если новый шаг
  приходит, пока пользователь не отматывал от `You`, вид сам подъезжает к
  новой позиции — не остаётся на устаревшем месте. Отмотанный назад вид
  никогда не дёргает сам по себе — только явное действие пользователя
  возвращает его к `You`.
- **Небольшая кнопка «вернуться на место».** Пока вид отмотан назад (тень
  видна) — в углу сцены появляется маленькая круглая кнопка-компас; тап по
  ней анимированно (не мгновенно) везёт `_panMeters` назад к `You`, тем же
  правилом, что и будущий якорь `You >` выше. Исчезает сама, как только вид
  снова на `You`. `_JourneyPathViewState._returnToYou()`, отдельная от
  перетаскивания `AnimationController` — драг в процессе прыжка его
  останавливает, а не борется за `_panMeters`.

Решено 2026-08-30 (§8, "повторный вход" — уточняет апгрейд аккаунта из
«Решено 2026-08-23»):

- **Повторный вход тем же Google-аккаунтом на новом устройстве/после
  переустановки больше не тупик.** Раньше `AuthController.upgradeWithGoogle()`

  происходил, прогресс и друзья с другого устройства оставались недоступны.
  Теперь вместо ошибки сессия **переключается** на уже существующий аккаунт

  вместо `linkWithCredential`) — `GoogleUpgradeOutcome.existingAccountRestored`.

  `currentUidProvider`); прогресс квеста — нет (drift ключуется на
  константный `localOwnerId`, не на uid, §5.2) — понадобилась отдельная
  сверка: `AuthController._reconcileProgressWithCloud` сравнивает локальный
  прогресс устройства с `users/{uid}/progress`-документом аккаунта
  (`ProgressSyncRepository.fetchCurrentProgress`, `isCurrent == true`) и
  **оставляет больший** — явный запрос при пересмотре плана, не мердж и не
  слепая победа облака. Если больше локальный — облачный документ
  дописывается локальным значением (`pushProgress`), чтобы третье
  устройство не увидело устаревшую меньшую цифру. Если больше облачный —
  `ProgressRepository.restoreFromCloud` перезаписывает локальные
  `StepIntervalRecords` этого `(ownerId, journeyId)` одной seed-записью,
  `SelectedJourney.reload()` подхватывает. Firestore Security Rules не
  менялись — `isSelf(uid)`-чтение своей же `progress`-подколлекции уже

  несколько дней считаются по фолбэку "меньше 3 дней данных" — полной

- **Не блокирует MVP и не меняет Firestore** — это чисто локальная,

Решено 2026-09-03 (§6.1 — вымышленное сюжетное время неба вместо реального
часов устройства, по прямому запросу «время должно быть не реальным, а

  время суток, в которое персонаж вышел по сюжету (Троя — рассвет), между

  обычная прогулка (условно 2 часа ≈ 10 км) никогда не пролистывала
  сразу несколько сюжетных суток, `journey_timing_repository.dart`'s
  `parseJourneySegmentTimings` бросает `FormatException`, если
  `durationDays` сегмента превышает `(toMeters - fromMeters) / 10_000`

  правила два эпизода с буквальным «девять дней» из текста
  (`storm-cape-malea`, `adrift-alone`) получили уменьшенную длительность
  (6 и 7 дней соответственно) — отмечено в их `timeNote`; многолетние
  эпизоды-выбросы (месяц у Эола, год у Цирцеи, семь лет у Калипсо)
  сжаты до ≈6–7 вымышленных дней той же логикой, а не буквальной
  мифической длительностью — иначе короткий по метрам участок карты
  мигал бы через сотни/тысячи циклов дня и ночи.
- **Аддитивно — квесты без такого контента не тронуты.** `SkyGradient`
  (`sky_gradient.dart`) получил опциональный `fictionalHour` — `null`
  (дефолт, и любой квест без `locations.json`-таймингов) сохраняет
  ровно прежнее поведение: реальные часы устройства, опрос раз в минуту.

  `tryLoadJourneySegmentTimings` (по образцу `quest_map_repository.dart`'s
  `loadQuestMap`): отсутствие `locations.json` у квеста мягко даёт
  `null` (fallback), а битый контент у квеста, который файл всё же
  поставляет, — бросает `FormatException`, а не тихо откатывается.
  Провайдер `selectedJourneySegmentTimingsProvider`
  (`journey_timing_providers.dart`, кодоген `@riverpod`, по образцу
  `quest_map_providers.dart`) читает `journey_flame_scene_view.dart`,
  которая передаёт `fictionalHourFor(timings, panMeters.round())` в
  `SkyGradient` тем же `_panMeters`, которым уже двигает ландшафт и

  рядом с ней. Подробности и как заменить на настоящий арт —
  `assets/journeys/tower-of-lights/README.md`. Ничего в коде не читает
  `map.webp`/`map.json` иначе для одного квеста и для другого — Карта и
  сцена «Путь» уже были общими для любого количества/длины квестов
  (`terrain_layer.dart`'s заглушечный ландшафт не завязан на конкретный
  биом, §9.1), так что второй квест заработал без изменений в этом слое.
- **Не использован механизм скачивания по требованию**
  (`journey_asset_catalog.dart`, решено 2026-09-04) — этот квест, как и
  «Одиссея», зашит в сборку (`pubspec.yaml`, без записи в
  `journeyAssetManifests`). Причина:
  ничего в `quest_map_providers.dart`/сцене «Путь» пока не умеет читать
  скачанные файлы вместо `AssetBundle` — тот механизм сегодня доводит
  оркестрацию скачивания и статусы карточки каталога до конца, но не сам
  путь чтения контента; переключить второй квест на него означало бы
  сначала реализовывать это недостающее звено, отдельная задача, не часть
  этого запроса.
- **Побочный бажный фикс, вскрытый вторым квестом:** пункт настроек
  «Одиссея (активный поход)» (§6.5 «themes») предполагал, что Одиссея —
  единственный квест, и был явно так закомментирован; с «Tower of Lights»
  в каталоге эта подпись стала способна врать (показывать «активный
  поход» рядом с темой, которая может не быть активной). Подпись упрощена
  до простого «Odyssey»/«Одиссея» — `settingsThemeOdyssey` в обоих ARB;
  сама механика выбора темы (§6.5 «themes») не изменилась.
- **Известный пробел, не устранённый этой задачей:** `achievementCatalog`
  (§6.3) не привязан к конкретному квесту — все пороги (`distanceReached`/
  `landmarkReached`) абсолютные метры, подобранные под 2 850 000 м
  «Одиссеи». Для 240 000-метрового «Tower of Lights» это означает, что
  почти весь список (все `landmarkReached`, все пороги выше 240 000 м)
  физически не может открыться, не крашится — но выглядит как пустой
  список трофеев без объяснения почему. Задокументировано в
  `achievement_catalog.dart`'s doc-комментарии; сделать трофеи per-quest —
  отдельная задача уровня архитектуры (§13 требует план), в открытых
  вопросах ниже.

Решено 2026-09-05 (§6.3, §9.1, §11 — три прямых запроса по следам «Tower of
Lights»: реалистичные трофеи для нового квеста, скрипт генерации карты в
репозиторий, русский перевод):

- **Трофеи теперь привязаны к квесту.** `AchievementDef` (`domain/
  achievement.dart`) получил поле `journeyId` (`String?`, `null` — общий
  порог, применим к любому квесту). Новая чистая функция
  `achievementsForJourney(catalog, journeyId)` — единственное место, которое
  его читает: с `journeyId == null` (квест ещё не выбран) отдаёт **весь**
  каталог без изменений — это уже существовавшее поведение экрана «Трофеи»
  до выбора квеста (витрина всех трофеев сразу), которое явно сохранено, а
  не сломано попутно; с выбранным квестом — только его собственные записи
  плюс общие. Оба потребителя каталога переведены на неё:
  `achievements_tab.dart`'s `evaluateAchievements` и
  `achievement_repository.dart`'s `refreshUnlocks`. Семь уже существовавших
  Одиссея-специфичных записей (`reached-circe`, `reached-lotus-eaters`,
  `halfway-there`, `reached-calypso`, `passed-scylla-charybdis`,
  `passed-sirens`, `journeys-end`) получили `journeyId: 'odyssey-ithaca'`;
  шесть по-настоящему общих порогов (`first-steps` … `long-hauler`) остались
  без `journeyId` — они и раньше не были завязаны на конкретный лор, только
  на число.
- **Семь новых трофеев для «Tower of Lights»** (`journeyId:
  'tower-of-lights'`), пороги — точные метры собственных ориентиров этого
  квеста (`assets/journeys/tower-of-lights/map.json`) либо доля от его
  240 000 м, тем же паттерном, что уже был у «Одиссеи»: `left-the-tower`
  (20 000 м), `crossed-the-pines` (50 000 м), `tower-halfway` (120 000 м,
  ровно половина), `reached-mountain-gate` (145 000 м),
  `reached-sea-horizon` (180 000 м), `reached-lantern-hill` (215 000 м),
  `under-the-skyfire` (240 000 м = вся длина квеста, поэтому это ещё и
  трофей завершения). У `under-the-skyfire` — **не** нейтральное название
  по образцу Одиссеиного `journeys-end`: если бы оба трофея завершения
  назывались одинаково («Journey's End»), витрина «нет выбранного квеста»
  (которая показывает оба одновременно, см. выше) отрисовала бы два тайла с
  одинаковым текстом — вместо этого `under-the-skyfire` назван по имени
  своего последнего ориентира, тем же «единственным исключением из
  нейтральных названий», что уже описан для `landmarkReached`-записей.
  Новые l10n-ключи — оба ARB; новые иконки — `achievement_illustrations.dart`'s
  `_classicIllustrations` (у `AppThemeId.classic`, которую этот квест и
  использует, §14 «themes»).
- **`generate_map.py` теперь в репозитории**
  (`assets/journeys/tower-of-lights/generate_map.py`), не только у Claude в
  песочнице — по прямому запросу. Переписан, чтобы читать ориентиры прямо
  из `locations.json` (не из отдельного фикстур-файла, которого больше нет)
  — `python3 generate_map.py` из этой директории перегенерирует
  `map.json`/`map.webp` без ничего дополнительного для синхронизации
  вручную. Прогнан заново и сверен с уже закоммиченными файлами — совпадает
  бит-в-бит, кроме самого текста `$schemaNote` (обновлён, чтобы называть
  сам скрипт) и завершающего перевода строки. Не часть `flutter build`/
  `flutter test` (§9.1 — не проектировать пайплайн генерации арта в коде):
  одноразовый инструмент для контента, который становится не нужен в
  момент, когда у квеста появится настоящая иллюстрация (README).
- **Русский перевод контента «Tower of Lights»** —
  `assets/journeys/tower-of-lights/locations.ru.json`, новый файл рядом с
  `locations.json`: только `segments[].name` и
  `landmarks[].name`/`narrative`, ключ — тот же `id`, что и в оригинале, а
  не полный дубль (метры/`departureHour`/`durationDays`/биом остаются в
  одном месте). `journey.name`/`pointA`/`pointB` не переведены — та же
  политика «данные каталога, не переводимый текст», что уже
  задокументирована в `quest_picker_view.dart`. Пока **мёртвый контент**:
  нарратив вообще нигде не подключён к экрану ни для одного квеста
  (`journey_flame_scene_view.dart` показывает заглушку "coming soon", не
  `locations.json`'s собственное поле `narrative`) — тот же статус, что и
  давно стоящий открытый пункт «перевести нарратив Одиссеи на ru» (он этим
  не закрыт, отдельный контент). README квеста объясняет оба пункта
